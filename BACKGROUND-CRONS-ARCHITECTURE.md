# Background opportunity-discovery crons — architecture

> Companion to the P0 write executors shipped in sessions 1–5. Those tools let
> the agent EXECUTE changes; these crons let it DISCOVER opportunities without
> burning real-time tokens during daily runs.

## Problem statement

Today's daily run does discovery + drafting in one shot:

1. Specialist reads GSC + GA4 + site crawl
2. Identifies meta gaps, content gaps, alt-text gaps, internal-link gaps
3. Drafts new content for one blog post
4. Files 2-4 manual_operator_task cards for the rest

This is expensive (re-discovers the same gaps every day) and brittle (single
run hits token budget mid-discovery, never reaches drafting). The audit cron
and backlink-analysis cron solve this for those two opportunity types by
running on schedule, writing to `seo_opportunities`, and letting the daily run
just pull from the bank.

We need the same pattern for the new opportunity types unlocked by sessions
1–5 (`framer_update_blog_meta`, `_body`, `_alt_text`, `add_internal_link`,
`add_site_schema`, `update_marketing_page_text`).

## Five new background scanners

Each runs on a schedule, scans for opportunities of its type, writes records
to `seo_opportunities` (using existing table — no new schema). Daily run
aggregator pulls from `seo_opportunities` as it already does for audit +
backlink findings.

### 1. `blog_meta_gap_detector` — daily

**Scans:** All blog posts (Framer CMS) for weak/missing meta titles and descriptions.

**Opportunity criteria:**
- Title >60 chars or <30 chars → "Title length out of optimal range"
- Title doesn't include any target keyword (cross-ref ranking_history) → "Title missing keyword"
- Description missing entirely → "No meta description"
- Description >160 chars or <100 chars → "Description length out of range"
- Description doesn't reflect post body intent (LLM judge) → "Description weak"

**Opportunity record:**
```json
{
  "type": "blog_meta_gap",
  "target_url": "/resources/<slug>",
  "current_title": "...",
  "current_description": "...",
  "issues": ["title_too_long", "description_missing"],
  "suggested_action": {
    "toolName": "framer_update_blog_meta",
    "toolInput": { "slug": "...", "newTitle": "...", "newDescription": "..." }
  },
  "priority": "P2"
}
```

**Daily-run consumption:** Aggregator surfaces top 1-3 in the daily Slack post
with the suggested action pre-filled. Agent files propose_action verbatim.
Operator approves → executor ships.

**Skeleton implementation** (see `src/cron/blog-meta-gap-detector.ts` after
session 6 lands).

---

### 2. `blog_alt_text_gap_detector` — weekly

**Scans:** All blog posts where the Image field has a value but no `altText`
(or empty altText).

**Opportunity criteria:**
- Image present, alt text missing or empty
- Image present, alt text is the filename (e.g. "hero-image.jpg") or generic ("image")

**Opportunity record:**
```json
{
  "type": "blog_alt_text_gap",
  "target_url": "/resources/<slug>",
  "current_alt": "",
  "suggested_action": {
    "toolName": "framer_add_blog_alt_text",
    "toolInput": { "slug": "...", "newAltText": "<generated based on post topic + image context>" }
  },
  "priority": "P3"
}
```

The suggested alt text is generated by feeding the post Title + first paragraph
+ image URL to an LLM with a "describe-this-image-for-SEO-and-a11y" prompt.

---

### 3. `internal_link_gap_detector` — weekly

**Scans:** Pairs of pages that should plausibly be internally linked but aren't.
Uses semantic similarity (existing pgvector setup) between page embeddings
plus rule-based "same cluster" detection.

**Opportunity criteria:**
- Page A and Page B are in the same keyword cluster (or embedding similarity > 0.75)
- No existing link from A → B (parse A's HTML, look for `<a href="...B">`)
- Both pages are indexed (not noindex'd)
- A's body contains text that semantically fits as anchor text for B

**Opportunity record:**
```json
{
  "type": "internal_link_gap",
  "source_url": "/resources/<slug-A>",
  "target_url": "/resources/<slug-B>",
  "suggested_anchor_text": "...",
  "suggested_action": {
    "toolName": "framer_add_internal_link",
    "toolInput": { "slug": "<slug-A>", "sourceText": "...", "targetUrl": "/resources/<slug-B>" }
  },
  "priority": "P2"
}
```

Note: targeted to blog posts only in v1 (uses `framer_add_internal_link`).
Marketing-page link gaps stay as manual_operator_task.

---

### 4. `schema_gap_detector` — daily

**Scans:** Site-wide JSON-LD presence (via setCustomCode read) cross-referenced
against business type.

**Opportunity criteria:**
- No `Organization` schema → P0
- No `WebSite` schema → P1
- For LocalBusiness-shaped tenants: no `LocalBusiness` schema → P0
- For service-business tenants: no `Service` or `ProfessionalService` schema → P1
- For content-heavy sites: no `BlogPosting` schema interpolation on blog template → P2 (manual_operator_task)

**Opportunity record:**
```json
{
  "type": "schema_gap",
  "schema_type": "Organization",
  "suggested_action": {
    "toolName": "framer_add_site_schema",
    "toolInput": { "schemaId": "organization", "jsonLd": "..." }
  },
  "priority": "P0"
}
```

The jsonLd is pre-constructed using tenant config (clientName, address, phone,
etc) so the agent doesn't need to re-research the business.

---

### 5. `content_decay_detector` — weekly

**Scans:** Blog posts ranking below position 10 for their target keyword, OR
posts older than 12 months with declining impression trend (cross-ref
ranking_history snapshots).

**Opportunity criteria:**
- Post ranking position 11-30 (top of "almost there" range)
- Or post older than 12 months with -20% impression trend
- Post body length seems thin relative to top 3 SERP competitors

**Opportunity record:**
```json
{
  "type": "content_decay",
  "target_url": "/resources/<slug>",
  "current_position": 14,
  "target_keyword": "...",
  "decay_signal": "ranking_stuck_p11_to_p30",
  "suggested_action": {
    "toolName": "framer_update_blog_body",
    "toolInput": { "slug": "...", "newContent": "<refreshed HTML>" }
  },
  "priority": "P1"
}
```

The `newContent` is generated by:
1. Fetching current body
2. Researching top 3 SERP competitors
3. Producing a refreshed body that addresses competitor differentiation

This is expensive (~50-80K tokens per opportunity) so cron runs weekly, not
daily, and only for posts meeting the criteria.

## Schedule summary

| Cron | Frequency | Approx token cost / run | Tenant scope |
|---|---|---|---|
| `blog_meta_gap_detector` | Daily | ~10K | per-tenant |
| `blog_alt_text_gap_detector` | Weekly | ~5K | per-tenant |
| `internal_link_gap_detector` | Weekly | ~30K (embeddings cached) | per-tenant |
| `schema_gap_detector` | Daily | ~5K | per-tenant |
| `content_decay_detector` | Weekly | ~50-80K per opportunity | per-tenant, top 10 candidates |

Total per-tenant weekly budget: ~100-150K tokens for full opportunity discovery.
For Tarino at $3/M input, $15/M output → ~$0.30-0.50/week for discovery.
Cheaper than running discovery inline every day.

## Daily run integration

After all five crons are operational, the daily run's specialist prompt
changes from "discover opportunities" to "draft from the bank":

```
The opportunity bank already contains:
- N blog_meta_gap entries
- N blog_alt_text_gap entries  
- N internal_link_gap entries
- N schema_gap entries
- N content_decay entries (highest priority)
- N backlink_prospect entries (existing)
- N audit_finding entries (existing)

Your job today is DRAFTING + ROUTING, not discovery:
1. For the top 1-2 content_decay entries, draft refreshed bodies and file
   framer_update_blog_body propose_actions
2. For the top 1-2 internal_link_gap entries, file framer_add_internal_link
3. For top 1-2 blog_meta_gap entries, draft improved title/description and
   file framer_update_blog_meta
4. For 1 new blog post topic gap (not in bank), draft and file approve_blog_pitch
5. Snapshot today's metrics
```

This collapses the daily run from a discovery+drafting marathon (the source
of today's token-exhaustion hangs) to a focused drafting pipeline. Token
budget per daily run drops by ~50%.

## Cron registration

Following the pattern of existing `audit` and `backlink_analysis` crons
(per memory: configured in `tenant_schedules` table, fired by BullMQ
repeatable jobs registered in `src/scheduler/index.ts`).

Each new cron gets a row in `tenant_schedules` per tenant:

```sql
INSERT INTO tenant_schedules (tenant_id, run_kind, cron_expr, enabled)
VALUES
  ('tarino', 'blog_meta_gap_scan',     '0 6 * * *',     true),
  ('tarino', 'schema_gap_scan',        '0 6 * * *',     true),
  ('tarino', 'blog_alt_text_gap_scan', '0 6 * * 1',     true),
  ('tarino', 'internal_link_gap_scan', '0 6 * * 1',     true),
  ('tarino', 'content_decay_scan',     '0 6 * * 0',     true);
```

(All UTC. Daily ones run at 6am UTC = 4pm Sydney; weekly Monday at same time;
content decay Sunday so refreshed bodies are ready for Monday's draft run.)

`bootstrapSchedules` registers each as a BullMQ repeatable; the worker
dispatches to the appropriate cron handler based on `run_kind`.
